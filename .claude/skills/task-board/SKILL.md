# タスクボード（`tm`）の使い方

人間と AI が**同じカンバンを共同管理する**ためのツール。人間はブラウザ、AI は `tm` CLI で同じサーバーを操作する。

## レーンは「いまボールを持っているのは誰か」

このボードの肝は、レーンが作業の進捗段階ではなく **責任の所在** を表していること。
人間は「あなたの判断待ち」だけ見ればよく、AI は「エージェント待ち」だけ拾えばいい。
だから **タスクを曖昧な状態で放置しないこと** が最も重要なルールになる。

| status | 意味 |
| --- | --- |
| `waiting_agent` | 人間があなたに依頼した。**あなたの受信箱** |
| `in_progress` | 誰かが作業中。`worker` に作業者名が入る |
| `waiting_human` | あなたが人間を待っている（`waiting_reason` が `question` = 質問 / `review` = 完了報告） |
| `todo` / `on_hold` / `done` | 未着手 / 保留 / 完了 |

## 基本ループ

```
tm inbox                  # 依頼されたタスクを見る（優先度・期限が高いものから）
tm show <id>              # 説明・完了条件・サブタスク・付箋・ファイル・履歴を読む
tm start <id>             # 着手（自分を作業者として記録）
tm note <id> "<進捗>"      # 途中経過を残す
tm check <id> 1,2         # 満たした完了条件にチェック
tm done <id> "<結果>"      # 完了（何をしてどう検証したかを書く）
```

途中で人間の判断が必要になったら、**推測で進めずに投げ返す**:

```
tm ask <id> "A と B のどちらにしますか？ A なら〜、B なら〜になります"
```

これでタスクは「あなたの判断待ち（質問）」に移り、ボード上のカードに質問文がプレビュー表示される。
人間が付箋で答えて再度依頼すると、また `tm inbox` に現れる。

## 完了条件（これがこのツールの中心）

タスクには**完了条件のチェックリスト**がある。`tm done` は**全条件がチェック済みでないと exit 3 で拒否される**。
これは「AI が『できました』と言ったが実は違った」を防ぐための仕組みなので、回避せずに付き合うこと。

- **完了条件が無いタスクを受け取ったら、まず条件を提案する。**
  何をもって完了かが決まっていない依頼は、だいたい後で認識がずれる。
  ```
  tm criteria add <id> "GET /api/health が 200 を返す"
  tm criteria add <id> "既存テストが通る"
  tm ask <id> "完了条件を上記のように置きました。これで進めてよいですか？"
  ```
- 条件を満たすたびに `tm check <id> <番号>`。番号は `tm show` に表示される 1 始まりの番号。
- どうしても全部は満たせないときだけ `tm done <id> "<残っていることと理由>" --partial`。
  これは完了にはならず「完了報告」として人間の確認待ちに入る。ごまかすより正直に部分報告するほうがいい。
- `tm done` の結果メモは必須。**何を変えて、どう検証したか**を書く。「完了しました」だけでは人間が判断できない。

## 書くときの心得

付箋（メモ）は 300 文字まで。**人間はこれをスマホのカードで読む**ので、要点から書く。

- 良い: `src/server.js のルーティングを実装。npm test で 32 件通過。残りは SSE の再接続テスト。`
- 悪い: `作業を進めました。おおむね順調です。`

具体的なファイルパス・実行したコマンド・計測した数値を入れると、人間がそのまま判断に使える。
ユーザーが日本語で話しているなら、付箋も日本語で書くこと（ボードの UI は日本語）。

長い出力やモックアップは付箋に貼らず添付する:

```
tm attach <id> mockup.html     # .html はボードの HTML タブでプレビューされる
tm attach <id> bench.csv
```

## やってはいけないこと / できないこと

ポリシーで守られているので、違反すると exit 2 で拒否される。回避を試みないこと。

- タスクの削除（`tm rm`）は人間のみ。
- 人間が書いた付箋・完了条件の編集や削除は不可（チェックを付けるのは可）。
- 他人の操作の取り消しは不可。**自分の操作なら取り消せる**:
  ```
  tm history <id>            # h12 のような履歴 id が出る
  tm revert <history_id>     # 1 操作だけ元に戻す
  ```
  誤操作に気づいたら、隠さずその場で戻して付箋で一言書く。全操作は「誰が・いつ・何を」で記録されている。

そして最重要: **作業を中断するときにタスクを `in_progress` のまま放置しない。**
`tm ask`（質問）・`tm done`（完了）・`tm hold <id> "<理由>"`（保留）・`tm handoff`（人間に戻す）のどれかで、
必ずボールの持ち主をはっきりさせてから離れること。誰も見ていないタスクが一番の損失になる。

## 前提の確認

サーバーが動いていないと何もできない。疎通確認:

```
tm lanes                   # レーン一覧が出れば疎通 OK
```

`cannot reach ...` が出たら、ボードのリポジトリで `npm start`。環境変数:

| 変数 | 既定 | 用途 |
| --- | --- | --- |
| `TM_URL` | `http://127.0.0.1:3000` | サーバーの場所 |
| `TM_ACTOR_NAME` | `agent` | 履歴・付箋に残る自分の名前。`claude-code` など識別できる名前を設定する |
| `TM_ACTOR` | `agent` | `human` にすると人間として操作する。通常は変えない |
| `TM_TOKEN` | なし | サーバーがトークン保護されている場合 |

複数のエージェントが同居する環境では `tm start` が他のエージェントの作業中タスクに対して exit 4 で失敗する。
その場合は横取りせず、別のタスクを拾うか、本当に引き取るべきときだけ `--force` を使う。

## 出力を機械的に扱う

`--json` を付けると完全な JSON が返る。スクリプトから使うときはこちら。

```bash
tm --json inbox | jq -r '.[] | "\(.id)\t\(.priority)\t\(.title)"'
tm --json show 12 | jq '.criteria[] | select(.done == false) | .text'
```

終了コードで分岐できる:

| code | 意味 |
| --- | --- |
| 0 | 成功 |
| 1 | 一般エラー（サーバー未起動、引数不正など） |
| 2 | ポリシーで禁止された操作 |
| 3 | 完了条件が未達（`tm done`） |
| 4 | 競合（他のエージェントが作業中、楽観ロック衝突、取り消し済み履歴の再取り消し） |
